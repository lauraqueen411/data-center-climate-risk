## Task 2 — LOCA2 humidity loader (not MACA — confirmed available on the HPC)

**Superseded plan:** the original version of this task doc had you build a MACA loader. Don't — MACA is CMIP5-era data, while the LOCA2 temperature pipeline is locked to a single CMIP6 GCM/member (ACCESS-CM2, r1i1p1f1). Pairing CMIP5 humidity with CMIP6 temperature means the two fields wouldn't represent the same simulated climate realization. Use the **LOCA CMIP6 humidity companion dataset** (Pierce & Cayan, Scripps/UCSD) instead — it's downscaled on the same 1/16° LOCA2 grid and computed directly from LOCA2's own downscaled Tmax/Tmin, so it's internally consistent with the temperature data already in use, not just topically similar. `docs/methods-document.md`'s Data Sources table and Section 1.2 have already been updated to reflect this swap.

**Confirmed present on the HPC** (actual `ls` output, both historical and ssp585 checked):

(`hursmax/` mirrors `hursmin/` in both scenarios.)

Note the directory layout differs from the existing LOCA2 temperature path (`run_heat_processing.py`'s `_loca2_file`, rooted at `.../LOCA2/CONUS_regions_split/<model>/n_west/0p0625deg/<member>/<scenario>/<variable>/...`): the humidity tree has **no `n_west` regional-split level** (`<model>/0p0625deg/<member>/<scenario>/<variable>/...`), and filenames have **no `.n_west` suffix** and a different version stamp (`v20250218` vs. the temperature files' `v20220413`). Variable names are `hursmax`/`hursmin`, not `rhsmax`/`rhsmin`. Each daily `.nc` file has a sibling `.monthly.nc` aggregate — **filter these out**, same as `_loca2_file`'s existing fallback already does for `.monthly.`/`.yearly.` (reuse that filter, don't reinvent it).

**Important — ssp585 is split into three non-overlapping windows, not one file:** `2015-2044`, `2045-2074`, `2075-2100`. There is no single file covering the full `2015-2100` span the way `_loca2_file`'s primary (non-fallback) lookup expects for temperature. The two future periods used throughout this project (`2045-2074` mid-century, `2075-2100` end-of-century — see `docs/tasks/0.2-fix-loca2-window-resolver-and-time-horizons.md`) were chosen to match these native windows exactly, so the resolver just needs to pick the correct single file per period — no concatenation required.

**Flag this back to the user before proceeding — likely affects already-"closed-out" 1.1 heat work, not just this task:** `_loca2_file`'s own docstring/comments acknowledge "some future files are split by shorter windows," and its fallback logic explicitly picks the *single* file whose window has `end >= 2099` (i.e., it would pick `2075-2100` and only that file). If they are, tell the user immediately — that's a correctness bug in already-reported results, out of scope to silently fix as a side effect of this PUE task.

## Task 3 — Daily pairing assumption

**[paper-verified — this is a bigger deviation than it might look]** Section 3.4 of the paper states the model was built and validated using weather data at **hourly resolution**. Switching the humidity source to the LOCA CMIP6 companion (Task 2) fixes the *spatial/GCM-lineage* consistency problem, but not this one: LOCA2 temperature and its humidity companion still only give daily tasmax/tasmin + hursmax/hursmin, not hourly (T, RH) pairs, so running this model on daily data remains a genuine step down in temporal resolution from how it was validated — not just a minor implementation detail. Document this prominently in the Assumptions log (not a passing mention), and use an explicit, documented pairing to approximate a representative daily PUE — e.g. pair Tmax with RHmin and Tmin with RHmax (typical diurnal anti-correlation), compute PUE at both, average for the day, then average across the period. **Don't pick a different approach silently without flagging it, and don't understate the hourly-vs-daily gap when you write up the assumption.**
