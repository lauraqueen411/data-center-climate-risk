It blocks 1.2 too, since `run_pue_processing.py` (per `docs/tasks/1.2-pue-analysis.md`) was about to inherit the same broken assumption.

**Revised 2026-08-20, same day as first written:** the original version of this doc had the two new future periods (2036-2065, 2070-2099) straddling two windowed files each, requiring general multi-file concatenation logic. User decided to simplify instead — **use the HPC's native file windows directly as the periods**, rather than picking round-number decades and building concatenation to serve them. Read `docs/methods-document.md`'s "Time Horizons" section and `docs/code-development-plan.md`'s "1.1 Acute heat risk — REOPENED" entry first.

## The bug

`run_heat_processing.py`'s `_loca2_file` resolves a future-scenario file by first trying a canonical `2015-2100` filename, and falling back to globbing for a file whose year-window `end >= 2099`. Confirmed via `ls` on the HPC (2026-08-20) that ssp585 files are actually split into three non-overlapping windows:

```
tasmax.ACCESS-CM2.ssp585.r1i1p1f1.2015-2044.LOCA_16thdeg_v20220413.n_west.nc
tasmax.ACCESS-CM2.ssp585.r1i1p1f1.2045-2074.LOCA_16thdeg_v20220413.n_west.nc
tasmax.ACCESS-CM2.ssp585.r1i1p1f1.2075-2100.LOCA_16thdeg_v20220413.n_west.nc
```

(plus `.monthly.` and `.yearly.avg.`/`.yearly.` siblings for each window, already correctly filtered out by the existing daily-file glob)

The fallback's `end >= 2099` filter matches only the `2075-2100` file. `RunConfig`'s old future period, `2070-2099`, was then subset from that one file, silently yielding **2075-2099 (25 years) instead of the intended 30** — 2070-2074 was never loaded at all. This affects every ssp585 output in `outputs/month2_heat/` — rasters, PNGs, `facility_heat_indices.csv`.

The LOCA CMIP6 humidity companion data (`docs/tasks/1.2-pue-analysis.md`, Task 2) is windowed identically, so this isn't a one-off to LOCA2 temperature.

## New time horizons — snapped to the native windows (see methods doc for full rationale)

Three periods everywhere heat/PUE periods are used:

- **Historical:** `1985-2014` (changed from the old `1950-1979` — see methods doc's "Time Horizons" section for why. Still a subset of the single historical file, 1950-2014, not a windowing issue — but `RunConfig.hist_start`/`hist_end` need updating in Task 2 below, and any already-generated historical-period output needs regenerating alongside the future-period rerun, not just the future side.)
- **Mid-century (new primary period):** `2045-2074` — the native middle window, used **as-is, whole**
- **End-of-century (conservative secondary period):** `2075-2100` — the native last window, used **as-is, whole**

Both future periods now map to exactly one file each, with no subsetting needed at all beyond opening the file — `select_year_range` becomes unnecessary for these two periods (the whole file's time range *is* the period), though it's harmless to keep as a defensive assertion that the loaded file's span matches what was expected.

**Note the resulting windows aren't equal length** (mid-century is 30 years, end-of-century is 26 years, 2075-2100 inclusive) — that's a direct consequence of using the native splits rather than round decades. Document this as a stated simplification in the Assumptions log, not a silent mismatch.

**Also note:** the old buggy output (2075-2099) is coincidentally almost identical to the new end-of-century window (2075-2100) — it's short by exactly one year (2100). The mid-century window (2045-2074) is genuinely new, though — the old pipeline never loaded that file at all.

## Task 1 — Fix the resolver to select the correct native-window file per period

- Replace `_loca2_file`'s `end >= 2099` heuristic with exact matching: given a requested period's `(start_year, end_year)`, return the file whose filename window matches exactly (`2045-2074` or `2075-2100`) — not the first file found past some threshold. Raise a clear error if no exact match exists, rather than silently falling back to something close.
- Move it out of `run_heat_processing.py` into a shared module (e.g. `climate_risk_dc/climate/loca2_io.py`) so `run_heat_processing.py` and the new `run_pue_processing.py` (1.2) both use the same resolver — per `CLAUDE.md`'s reuse-over-duplication convention.
- Add an equivalent resolver for the LOCA2 humidity companion's directory layout — see `docs/tasks/1.2-pue-analysis.md` Task 2 for that path structure, which differs from the temperature path (no `n_west` level, different version stamp) but uses the same window boundaries.
- Add a unit test that would have caught the original bug: assert that requesting the `2045-2074` period resolves to the `2045-2074` file (not `2075-2100`), and that requesting `2075-2100` resolves to that exact file and includes data through year 2100 (not silently capped at 2099).
