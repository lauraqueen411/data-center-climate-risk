## Task 1 — Facility-level heat index table

**Problem:** The six heat rasters (`cdd`, `tmax_threshold_days`, `heatwave_events` × historical/future) are currently only sampled at *generator* locations inside `build_dependency_table.py`. There is no clean table of these values at the data centers' own coordinates, which is the actual output Section 1.1 of the methods doc describes ("exceedance-day counts and peak severity, historical vs. future" — per facility).

**Do:**
1. Add a function (either a new `scripts/extract_facility_heat_indices.py` or a function added to `run_heat_processing.py`'s `run()` — your call, but keep it separable from the raster-generation step so it can be re-run without recomputing rasters) that:
   - Loads the Oregon data center points.
   - Samples all six existing rasters (paths already defined in `build_dependency_table.py`'s `rasters` dict — reuse that path convention) at each facility's `lon`/`lat` using `_sample_raster_values`.
   - Writes one row per facility to `outputs/month2_heat/facility_heat_indices.csv` with columns: `facility_id`, `facility_name`, `facility_lon`, `facility_lat`, then the six raster values (name them consistently with the existing `cdd_historical_1950_1979` / `cdd_ssp585_2070_2099` style used elsewhere in the repo), plus a derived `tmax_threshold_days_delta` and `heatwave_events_delta` (future minus historical) since "how failure risk changes over time" is the stated output.
2. Confirm output row count equals the number of Oregon facilities (no silent drops from failed raster sampling — `rasterio`'s `.sample()` returns `nodata`/NaN outside raster bounds, so assert no facility falls fully outside the raster extent, and fail loudly if one does rather than emitting a silent NaN row).

**Acceptance check:** Run against real Oregon data + already-generated rasters and confirm the row count matches the DC atlas count, and that historical vs. future deltas are all non-negative for both threshold-days and heatwave-events at every facility (sanity check — Oregon should not get *fewer* extreme heat days under SSP585 mid-century; if any are negative, treat that as a bug to investigate, not a value to report).

## Task 2 — Elevation-based threshold adjustment

**Problem:** The methods doc says the 35°C exceedance threshold (currently a flat constant, `HeatIndexConfig.threshold_c`) should be "adjust[ed] downward at higher-elevation sites where cooling performance drops." No elevation data or adjustment logic exists yet anywhere in the repo.

**This task has a data dependency the plan hasn't resolved yet:** the full USGS 3DEP elevation pipeline is scoped for flood work (Phase 2.2, `src/climate_risk_dc/flood/elevation.py`), which may not exist yet when you pick this up. Don't block on it — build a minimal, standalone elevation-extraction function now:

1. Add `get_facility_elevation_m(lon, lat, dem_path)` — a thin wrapper, same pattern as `_sample_raster_values`, sampling whatever DEM raster is available (ask the user which DEM file/path to point it at if `data/` doesn't already have one — do not silently fabricate a source). Place it somewhere reusable, e.g. `src/climate_risk_dc/geo.py` (it's a generic raster-at-point sampler, consistent with what's already there) rather than inside `climate/heat_indices.py`, so Phase 2.2's flood work can call the same function later instead of duplicating it.
2. In `heat_indices.py`, add a function `elevation_adjusted_threshold(base_threshold_c, elevation_m, config)` implementing whatever specific lapse-rate/derating relationship you use — **the methods doc does not specify the exact adjustment formula or rate**, so don't invent a precise number silently. Use a clearly documented placeholder rate (e.g. a simple, referenced psychrometric/standard-atmosphere lapse rate) and flag it in the function's docstring as an assumption to be confirmed against ASHRAE guidance or refined later, exactly the way other assumptions in this repo are logged (see the "Assumptions log" docstring pattern in `build_dependency_table.py`).
3. Re-run Task 1's facility-level extraction using the elevation-adjusted threshold instead of the flat 35°C constant, and add the adjusted threshold value used per facility as a column in `facility_heat_indices.csv` so it's auditable.

**Acceptance check:** Spot-check that higher-elevation Oregon facilities (if any exist in the DC atlas — check `sqft`/`elevation` distribution first) get a lower effective threshold and correspondingly higher exceedance-day counts than they would under the flat threshold; report the before/after delta for at least one such facility in your summary.

## Task 3 — Document the single-GCM decision

**Problem:** `run_heat_processing.py`'s `RunConfig` hardcodes `model: str = "ACCESS-CM2"`, `member: str = "r1i1p1f1"` with no documented rationale for using a single GCM rather than a multi-model LOCA2 ensemble.

**Do:** Don't change the code behavior. Add a short paragraph to the module docstring of `run_heat_processing.py` (in the existing "Assumptions" style) stating explicitly: this pipeline uses a single GCM/member rather than an ensemble, what that means for uncertainty (single-model runs don't capture inter-model spread — results represent one plausible trajectory, not a probabilistic range), and that this is a known limitation to revisit if time allows extending to a multi-model set. Flag this same point back to the user rather than silently deciding whether to extend to an ensemble — that's a scope/cost decision, not a code decision.
